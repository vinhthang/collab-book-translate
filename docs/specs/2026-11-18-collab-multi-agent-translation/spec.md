# Collaborative Multi-Agent Book Translation on GitHub

- Feature ID: 2026-11-18-collab-multi-agent-translation
- Type: enhancement
- Status: In-Testing
- First entered In-Testing: 2026-11-18
- Related specifications: Implemented: Replaces [2026-11-06-collab-multi-agent-translation](../2026-11-06-collab-multi-agent-translation/spec.md)

## Problem and source intent

Enable multiple autonomous AI agents and human contributors on GitHub to collaboratively translate public-domain and openly licensed books (`en->vi` and `zh->vi`) inside a standalone public repository (`collab-book-translate`), coordinated by a local main agent with deterministic validation, peer review, live multi-dimensional evaluation, terminology governance, and GitHub Release publication.

Authorizing user intent and owner governance resolutions:

1. Core workflow intent (2026-11-06, verbatim user prompts): *"I want to do a book translate, the main again will break the book into trunks, then other agent could take task and translate, make pull request, then other agent could do the review, and comment + make score to the translate work"*; *"the main agent can do the final review and merge the request"*; *"when all the trunk (chapter) is done, then the work is done, main agent will produce the final book, and publish it"*; *"use git branch for each book, anyone can submit their book, like merge quest to books folder, the main agent can based on that merge branch and work with that book"*.
2. Standalone repository & zero-fallback plugin configuration (2026-11-06 to 2026-11-07, verbatim user prompts): *"I want this will be on a new repository, and new project as well, use this project as reference"*; *"you need to create config file for the plugin, do not fallback, but create config file for me"*; *"the rtk will be append outside of this plugin"*.
3. Prior grill decisions carried forward from [2026-11-06-collab-multi-agent-translation](../2026-11-06-collab-multi-agent-translation/spec.md): GitHub issues and labels as sole task state (no task hub, no GitHub Actions, no inbound webhooks); login-based contributor identity; seed-then-parallel terminology (`book_record.json` seeded on `ch01`, later terms proposed in `analyze_additions.json` and bound only at merge); engine-agnostic contributors with declared provenance; `en->vi` and `zh->vi` v1 scope; human licence gate; 24 h competing-PR window; 48 h starved-chapter bot fallback; 3-round revision cap; hourly/manual idempotent local sweep; EPUB 3, PDF, and DOCX published only as GitHub Release assets.
4. Re-review scope authorization (2026-11-18, verbatim user prompt *"go with your option 1 for these decisions"*): (a) whole-package replacement superseding `2026-11-06-collab-multi-agent-translation` upon reaching `In-Testing`; (b) `collab_seed.py` initializes `book_record.json` (sampling `min(3, N)` opening chapters to bound LLM cost while later chapters propose terms via `analyze_additions.json`) and opens/merges a bot-authored `ch01` seed PR with a bound-glossary audit comment, and `collab_sweep.py` automatically translates 48 h starved chapters and opens a normal competing PR; (c) sub-chapter splitting (`chNN-pK`) descoped to `Non-goals` for v1 (`1 chapter = 1 chunk`); (d) `config.json` gitignored in the public repository while `config.example.json` remains tracked.

## Non-goals

- **No external task hub (`review.vinhthang.dev`)**: GitHub issues, pull requests, comments, and labels are the sole task and state surface.
- **No GitHub Actions CI or inbound webhooks**: All checks, evaluations, merges, and releases run from the local main-agent sweep or manual CLI invocation.
- **No self-hosted Git server deployment**: No Gitea or Forgejo infrastructure in this specification.
- **No target languages other than Vietnamese (`vi`) in v1**: Only `en->vi` and `zh->vi` are accepted; other pairs are deferred to a separate specification.
- **No sub-chapter splitting (`chNN-pK`) in v1**: Every extracted chapter `chNN` maps 1-to-1 to a single translation task (`<slug>-chNN`).
- **No Git LFS source ingestion in v1**: Git LFS pointer files are rejected at intake; every submitted source file must satisfy `max_source_bytes` directly.
- **No audio, illustration, or web-reader pipelines**: Out of scope and excluded from `collab-book-translate`.
- **No external shell token-reduction wrappers inside executable plugin files**: External CLI wrappers are appended by the caller outside this repository, never embedded inside `scripts/`, `tests/`, `plugin.json`, `config*.json`, `.github/`, or `CONTRIBUTING.md`.

## Requirements

### REQ-016: Zero-fallback plugin configuration schema and local config hygiene

- Source intent: Verbatim user prompts (*"you need to create config file for the plugin, do not fallback, but create config file for me"*; *"the rtk will be append outside of this plugin"*) and 2026-11-18 Option 1 decision (`config.json` gitignored, `config.example.json` tracked).
- Statement: WHEN any collaborative CLI or workflow module loads plugin settings, THE configuration loader SHALL resolve the JSON file from explicit `--config`, `COLLAB_CONFIG_PATH`, or `<engine_root>/config.json` (where `<engine_root>` is the repository root directory containing `plugin.json`), without silent defaults, and SHALL validate all 14 required keys and domains:
  - `workspace_dir` (non-empty `str` path), `repo_full_name` (`str` matching `^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$`), `bot_login` (non-empty `str`), `bot_git_name` (non-empty `str`), `bot_git_email` (non-empty `str`), `human_approver` (non-empty `str` with `human_approver != bot_login`),
  - `window_hours` (`int | float > 0`), `fallback_hours` (`int | float > 0`), `max_revise_rounds` (`int >= 1`, not `bool`), `max_source_bytes` (`int > 0`, not `bool`),
  - `evaluation_engine` (`"workbuddy" | "cbc"`), `release_formats` (comma-separated non-empty subset of `{"epub", "pdf", "docx"}`), `allowed_licenses` (non-empty list of non-empty `str`), and `supported_pairs` (non-empty list of 2-element `[source_lang, target_lang]` string pairs).
  `config.json` SHALL be excluded via `.gitignore` and untracked in Git, `config.example.json` SHALL remain tracked, and tracked `plugin.json` SHALL be updated to declare `"config_example": "config.example.json"` alongside `"config": "config.json"`.
- AC-016-1 — Success: Loading a valid 14-key JSON file populates `CollabConfig` with exact normalized types, `.gitignore` excludes `config.json`, `git ls-files config.json` is empty, `config.example.json` is tracked, `plugin.json` is tracked with both `"config"` and `"config_example"`, and zero `rtk` tokens or `/Users/` paths appear across `scripts/`, `tests/`, `plugin.json`, `config.example.json`, `.github/`, and `CONTRIBUTING.md`.
- AC-016-2 — Boundary/failure: IF the resolved configuration file is missing, invalid JSON, missing any of the 14 keys, violates any field type/domain/positivity rule, or sets `bot_login == human_approver`, THEN `load_collab_config` SHALL raise `ConfigError` immediately and CLI entrypoints SHALL exit non-zero without falling back to `Path.cwd()` or hardcoded defaults.

- Source intent: Verbatim user prompt (*"use git branch for each book, anyone can submit their book, like merge quest to books folder"*) and 2026-11-18 re-review findings (`P1-7`, `P1-13`, `P2-5`, `P2-7`).

- AC-017-1 — Success: A `book/<slug>` PR for a new `<slug>` with a valid `manifest.json` and one non-LFS readable source file within `max_source_bytes` whose extracted chapters each fit within `1..2,000` segments and $\le 2,621,440$ bytes passes intake validation, and `.github/PULL_REQUEST_TEMPLATE/book.md` plus `CONTRIBUTING.md` document the `max_source_bytes` (`50 MiB` default in `config.example.json`) and per-chapter caps without Git LFS instructions.
- AC-017-2 — Boundary/failure: IF `<slug>` fails the regex, OR `books/<slug>/` or `runs/<slug>/` already exists on `main`, OR changed files touch any other path or multiple source files, OR the source file is a Git LFS pointer, unreadable, exceeds `max_source_bytes`, or extracts any chapter with `0` segments, $> 2,000$ segments, or $> 2,621,440$ UTF-8 bytes, OR `manifest.json` fails schema validation, OR sample text mismatches `source_lang` / has $\ge 5\%$ Vietnamese diacritic density, THEN THE main agent SHALL reject intake and post a PR comment naming every defect without merging or seeding.

### REQ-018: Commit-bound bot pre-screen and deadlock-free human licence approval gate

- Source intent: Verbatim user decision (*"The agent pre-screens, a human decides"*), `D1` dedicated bot identity, and re-review findings (`P0-2b`, `P1-1`, `P1-3`, `P1-5`, `P2-9`).
- Statement: WHEN an open `book/<slug>` PR at commit `<head_oid>` is swept, THE main agent (`bot_login`) SHALL post a pre-screen summary comment tagged `[collab-prescreen sha=<head_oid> status=PASS|WARN|FAIL]` (if no `bot_login`-authored `[collab-prescreen sha=<head_oid> ...]` comment already exists): `FAIL` when `REQ-017` or `REQ-019` structural/language/bounds validation fails; `WARN` when `REQ-017` and `REQ-019` pass but `license` is outside `allowed_licenses` or `<original>` triggers a `REQ-023` prompt-injection warning; and `PASS` when `REQ-017` and `REQ-019` pass, `license in allowed_licenses` (defaulting in `config.example.json` and `CONTRIBUTING.md` to `public-domain`, `CC0-1.0`, `CC-BY-4.0`, `CC-BY-SA-4.0`, `owner-permission`), and zero injection warnings fire. Only `[collab-prescreen ...]` comments authored by `bot_login` SHALL be recognized, using the chronologically latest `bot_login` marker for `<head_oid>`. THE main agent SHALL merge the PR (`gh pr merge --match-head-commit <head_oid>`) when: (a) authoritative pre-screen is `PASS` and `human_approver` either submitted an `APPROVED` review with `commit.oid == <head_oid>` (`pr.author.login != human_approver`) or posted `/approve-intake <head_oid>` after the pre-screen (`pr.author.login == human_approver`); OR (b) authoritative pre-screen is `WARN` and `human_approver` explicitly posted `/approve-intake <head_oid>` after the `WARN` comment (recording explicit human override of the licence/injection warning). `FAIL` pre-screens are never mergeable.
- AC-018-1 — Success: A `bot_login`-authored pre-screen `PASS` book PR at `<head_oid>` merges with `--match-head-commit <head_oid>` upon commit-matching `APPROVED` review or `/approve-intake <head_oid>` (and a `WARN` PR merges only upon post-warning `/approve-intake <head_oid>` from `human_approver`), and `CONTRIBUTING.md` lists the default `allowed_licenses` matching `config.example.json`.
- AC-018-2 — Boundary/failure: IF the latest `bot_login` pre-screen for `<head_oid>` is `FAIL` or absent (ignoring forged `[collab-prescreen ...]` comments from non-`bot_login` accounts), OR pre-screen is `WARN` with only a generic `APPROVED` review instead of `/approve-intake <head_oid>`, OR approval comes from any login other than `human_approver`, OR the `APPROVED` `commit.oid` / `/approve-intake` SHA does not equal `<head_oid>`, THEN THE main agent SHALL NOT merge the PR.

Build `runs/<slug>/book_record.json` from `manifest.json` and the opening `min(3, N)` extracted chapters (`ch01..ch<min(3, N)>`), recording `book_slug`, `source_lang`, `target_lang`, `title`, `brief` (`{"genre": manifest.genre or "non-fiction", "author": manifest.author, "summary": "<non-empty str>"}`), `glossary` (`dict[str, str]` source-to-target map, seeded with technical terms when technical domain markers match), `terms` (`[{"source": str, "target": str, "match": "word", "case_sensitive": bool}]`), `names` (`[{"source": str, "target": str, "also_referred_to_as": list[str]}]`), and `pronouns` (`[{"pair": [str, str], "a_to_b": str, "b_to_a": str, "basis": str, "provisional": false}]`; legacy `character_pronouns` on pre-v2.0 books is accepted as a read alias without mutating published pilot files). ### REQ-022: Independent peer review and parseable 6-dimension rubric

- Source intent: Verbatim user prompts (*"other agent could do the review, and comment + make score to the translate work"*; login-based reviewer independence) and re-review finding `P2-2`.
- Statement: WHEN a `ch02..chNN` translation PR is evaluated for review completeness, THE validator SHALL count a review as valid if and only if `review.author.login != pr.author.login`, the review provides at least one non-empty inline diff review comment (`line_comment_count >= 1`) or segment-anchored note matching `\bS-\d{4}\b` in the review body, and the review body specifies all 6 rubric dimensions (`Fidelity`, `Fluency`, `Terminology`, `Register`, `Structure`, `Completeness`) with numeric scores in `[1.0, 5.0]` matching `(?i)\b(Fidelity|Fluency|Terminology|Register|Structure|Completeness)\b[^0-9\n]*([1-5](?:\.\d+)?)(?:\s*/\s*5(?:\.0)?)?`.
